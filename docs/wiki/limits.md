# 한계와 다음 단계

**알면서 안 한 것**과 **모르고 안 한 것**을 구분해 적는다.
포트폴리오 프로젝트에서 가장 나쁜 상황은, 자기 프로젝트의 약점을
남에게 처음 듣는 것이다.

여기 적혀 있으면 "판단"이고, 안 적혀 있으면 "누락"이다.

---

## 의도적으로 범위 밖 (YAGNI)

단일 서버 데모라는 목표에서 나온 결정. 물어보면 "안 했다"가 아니라
**"이 규모에서 필요 없어서 뺐다"**가 답이다.

| 항목 | 뺀 이유 | 필요해지는 조건 |
|---|---|---|
| 서버 분산 / 샤딩 | 단일 프로세스로 목표 규모 충족 | 룸 수가 단일 프로세스 한계를 넘을 때 |
| 계정 서버 분리 | 로그인 트래픽이 게임 트래픽에 묻힘 | 인증이 실제 DB를 치기 시작할 때 |
| 무중단 배포 | 데모 서버 | 실제 유저가 붙을 때 |
| 크로스플랫폼 | 클라가 DirectX11 Windows 전용 | 없음 |
| 직렬화 라이브러리 | 양쪽 다 C++/x64 (→ D-006) | 다른 언어 클라이언트가 생길 때 |
| 패킷 암호화 | 데모 | 실제 서비스 |

## 알고 있는 미해결 결함

상세는 [review-log.md](review-log.md). 여기엔 "무엇이 위험한가"만.

| 영역 | 현재 상태 | 항목 |
|---|---|---|
| **송신 경로** | 버퍼가 가득 차면 미전송 데이터를 덮어쓴다. 완료 콜백과 송신 요청 사이에 레이스가 있다 | R-001, R-002 |
| **동시성** | `PacketBuffer`가 두 스레드에 무보호 공유 | R-016 |
| **입력 검증** | 대부분의 핸들러가 패킷 크기를 검증하지 않고 캐스팅 | R-005 |
| **인증** | 비밀번호를 받지만 검증하지 않는다. 세션 토큰 없음 | R-009, D-008 |
| **세션 재사용** | 세대 값이 없어 패킷이 다른 유저에게 갈 수 있다 | R-010 |
| **로그인 상태** | UserID가 손상되어 중복 로그인 차단이 작동하지 않는다 | R-003 |

## 자원 배분의 불균형

[structure.md](structure.md) §9에서 바이트 단위로 세어본 결과.

| 항목 | 크기 | 상주 총량 | 비중 |
|---|---:|---:|---:|
| `User::PacketBuffer` 조립 버퍼 | 64 KB × 100 | 6,400 KB | **88 %** |
| `stClientInfo` 본체 (송신 버퍼 2개 포함) | 8.5 KB × 100 | 850 KB | 12 % |
| 나머지 | — | ~39 KB | <1 % |
| | | **≈ 7.3 MB** | |

**수신 버퍼는 256 B인데 조립 버퍼는 64 KB — 256배 차이다.** 최대 패킷이
`ROOM_CHAT_NOTIFY` 296 B이므로 조립 버퍼가 64 KB일 이유가 없다.
반대로 송신 버퍼 4 KB는 채팅 알림 14개면 차서 R-001을 유발한다.

**즉 큰 쪽이 필요 없고 작은 쪽이 모자란다.** 근거가 있는 값인지 확인이 필요하며
(→ decisions.md 열린 질문), Phase 4에서 조립을 세션으로 옮길 때 함께 재산정한다.
목표치는 [target-structure.md](target-structure.md) §9.

## 규모 한계 (측정 안 됨)

**아직 부하 테스트를 한 적이 없다.** 아래는 코드에서 유도한 이론값이며
실측이 아니다. 이 구분이 중요하다.

| 항목 | 값 | 근거 |
|---|---|---|
| 최대 동시 접속 | 100 | `MAX_CLIENT` — 세션 풀 크기. 하드 리밋 |
| 최대 룸 | 10 | `PacketManager::CreateComponent` 하드코딩 |
| 룸 정원 | 4 | 동상 |
| 최대 동시 인원 | 40 | 룸 10 × 4 |
| 세션당 송신 버퍼 | 4KB | `MAX_SOCK_SENDBUF`. `ROOM_CHAT_NOTIFY` 14개면 참 |
| 게임 로직 처리량 | 미측정 | 단일 스레드. 4인 룸 20Hz 동기화 = 룸당 초당 약 320 send |

**측정해야 할 것** — 포트폴리오에서 "출시 품질"을 주장하려면 숫자가 있어야 한다.

- [ ] 40명 접속 + 20Hz 캐릭터 동기화 시 ProcessThread 점유율
- [ ] 패킷 큐 최대 길이 (백프레셔가 필요한지 판단 근거)
- [ ] 접속 → 룸 입장 완료까지 지연
- [ ] 캐릭터 동기화 왕복 지연 분포 (p50/p99)

`DummyClient`를 다중 접속 부하 도구로 확장하는 것이 가장 싼 경로다.

## 품질 인프라 부재

| 없는 것 | 영향 |
|---|---|
| 자동화 테스트 | 회귀를 사람 눈으로만 잡는다. `PacketBuffer`의 분할/병합처럼 눈으로 못 보는 로직이 특히 위험 |
| CI | 빌드 깨짐을 커밋 후에 안다 |
| 메트릭 | 서버 상태를 로그로 추측한다 |
| 설정 파일 | 상수 변경에 재빌드 필요 (R-015) |
| 정상 종료 | `DestroyThread`가 in-flight I/O 완료를 기다리지 않는다 |

우선순위는 **테스트 > 메트릭 > CI > 설정**. 이유는 앞의 두 개가 나머지
작업의 안전망이기 때문이다. 특히 `PacketBuffer`는 부작용이 없는 순수 로직이라
테스트를 붙이기 가장 쉽고, 깨졌을 때 증상이 가장 이해하기 어려운 곳이다.
여기서 시작하는 게 투자 대비 회수가 가장 크다.

## 구조적으로 남은 것

기능 결함은 아니지만 설계 논의가 끝나지 않은 것들.

- **틱이 없다.** ProcessThread는 이벤트 구동 + 1ms sleep 폴링이다.
  고정 주기가 없어 이동 보간·타임아웃·주기적 정리를 걸 자리가 없다.
  캐릭터 동기화를 수신 즉시 브로드캐스트하므로 송신 횟수가 수신 횟수에
  비례한다 — 틱에 모아 보내면 줄어든다.
- **룸 동시성 모델 미확정.** 단일 스레드 유지 vs 룸 액터 (→ D-003).
- **서버 권위(authority)가 없다.** 클라이언트가 보낸 위치를 검증 없이
  그대로 뿌린다. `ClientIndex`가 진짜 송신자인지도 확인하지 않는다.
  지금은 신뢰 클라이언트 모델이며, 이건 **결함이 아니라 미결정 사항**이다.
  게임 장르가 정해지면 답이 나온다 (→ decisions.md 열린 질문).
- **프로토콜 버전 협상이 없다.** 클라/서버 빌드가 어긋나면 조용히 깨진다.
  핸드셰이크에 버전 필드 하나면 "조용히"가 "명확히"로 바뀐다.

## 이 문서 쓰는 법

- 무언가를 **안 하기로 결정**하면 여기에 한 줄 적는다. 그 순간이 가장 싸다.
- 결함을 발견했는데 **지금 안 고치기로** 했으면 여기 적고 review-log에서 링크한다.
- 해결되면 지운다. 이 문서는 원장이 아니라 **현재 상태 스냅샷**이다.
  이력이 필요하면 그건 [decisions.md](decisions.md)나 [review-log.md](review-log.md)의 몫이다.
