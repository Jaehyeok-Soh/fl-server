# 설계 결정 기록

이 문서가 이 위키에서 **가장 가치 있는 문서**다. 코드를 읽으면 *무엇을* 했는지는
알 수 있지만 *왜*와 *무엇을 버렸는지*는 영원히 알 수 없기 때문이다.

**제안하기 전에 여기부터 읽어라.** 이미 검토하고 버린 안을 다시 제안하는 것은
서로의 시간을 태우는 일이다.

## 기록 형식

```markdown
### D-000 — 결정 한 줄
| | |
|---|---|
| 상태 | 확정 / 잠정 / 재검토 예정 / 폐기(→ D-00X로 대체) |
| 날짜 | YYYY-MM-DD |
| 근거출처 | 사람 / 코드추정 |

**맥락** 어떤 문제를 풀려고 했는가.
**결정** 무엇을 골랐는가.
**버린 대안** 무엇을 왜 버렸는가.  ← 가장 중요한 칸
**결과** 실제로 어땠는가. 나중에 채운다.
```

**근거출처가 `코드추정`인 항목은 사람의 확인이 필요하다.** LLM이 코드만 보고
역추론한 것이라 의도와 다를 수 있다. 확인되면 `사람`으로 바꾼다.

### D-001 — 네트워크 I/O는 Windows IOCP
| | |
|---|---|
| 상태 | 확정 |
| 날짜 | (초기) |
| 근거출처 | 코드추정 |

**맥락** 다수 동시 접속을 처리해야 하고, 클라이언트가 DirectX11 자체 엔진이라

고민할 지점이 아니었을 수 있다.

### D-002 — 세션·유저·룸 사전 할당
| | |
|---|---|
| 상태 | 확정 |
| 날짜 | (초기) |
| 근거출처 | 코드추정 |

**맥락** 게임 서버는 접속/해제가 빈번하다. 매번 할당하면 단편화와 지연이 생긴다.

**결정** `IOCPServer::CreateClient`가 시작 시 `MAX_CLIENT`(100)개의
`stClientInfo`를, `UserManager::Init`이 같은 수의 `User`를,
`RoomManager::Init`이 `Room` 10개를 만든다. 이후 생성·해제 없음.
`Clear()`로 초기화만 한다.

이 결정에서 **I-3(인덱스 = 세션 ID)와 I-4(객체는 해제되지 않는다)**가 파생된다.
포인터가 무효화되지 않는다는 강력한 성질을 얻는 대신, "슬롯의 내용이 다른
유저 것으로 바뀌었는지"를 스스로 알 수 없다는 약점이 생긴다 (→ R-010).

**버린 대안** 접속 시 동적 할당 + `unordered_map<sessionId, Session>`.
유연하지만 할당 비용과 수명 관리가 붙는다.

**결과** 세대(generation) 값이 없어 R-010(패킷 오배달)이 생겼다.
결정 자체는 유효하고, 세대 값 8바이트로 약점만 메우는 것이 맞다.

### D-003 — 게임 로직은 단일 스레드
| | |
|---|---|
| 상태 | **잠정** — 룸 액터 모델 전환 논의 중 |
| 날짜 | (초기) |
| 근거출처 | 코드추정 |

**맥락** I/O는 4스레드로 병렬 처리하되, 게임 상태(유저·룸)의 동시성 문제를
피해야 한다.

**결정** `PacketManager::ProcessThread` 하나가 모든 패킷 핸들러를 실행한다.
I/O 스레드는 큐에 넣기만 한다. (→ I-1, I-2)

**버린 대안** *(사람 확인 필요)* 락으로 보호하며 워커 스레드에서 직접 처리.
`Room::m_RoomLock`이 남아있는 걸 보면 이 방향을 고려했거나 시작했다가
단일 스레드로 선회한 흔적일 수 있다 (→ R-013).

**결과 / 미해결**
- 이 결정의 이점을 코드가 **온전히 누리지 못하고 있다.** 단일 스레드인데
  룸에 mutex가 남아있고(R-013), 정작 진짜 공유 지점인 `PacketBuffer`는
  보호되지 않는다(R-016). 결정과 구현이 어긋나 있다.
- 룸당 4명 × 10룸 규모에서는 단일 스레드로 충분하다. 전환의 동기는
  처리량이 아니라 **"룸 내부는 단일 스레드"라는 불변식을 소유권으로 강제**하는 것.
- 전환 시 D-010으로 대체 예정.

### D-004 — SendThread를 만들었다가 비활성화
| | |
|---|---|
| 상태 | **잠정 — 사람 확인 필요** |
| 날짜 | (미상) |
| 근거출처 | 코드추정 |

**맥락** 송신을 별도 스레드가 8ms마다 모아서 처리하는 구조를 시도했다.

**결정** `IOCPServer::CreateSendThread`와 `SendThread`는 구현되어 있으나
`StartServer`에서 호출이 주석 처리되어 **꺼져 있다**. 현재는 `SendMsg` 호출
스레드(= ProcessThread)에서 곧바로 `WSASend`를 건다.

**버린 이유** *(미상 — 반드시 채워야 할 칸)*
전 세션을 8ms마다 순회하는 폴링 비용 때문인지, 지연이 늘어서인지,
아니면 그냥 디버깅 중 임시로 끈 것인지 코드만으로는 알 수 없다.

> **왜 껐는지 기억나면 여기에 적어줘.** 이건 나중에 R-001(송신 버퍼 재작성)을
> 설계할 때 직접 영향을 준다. 배칭이 필요 없다고 판단한 거라면 링버퍼만 고치면
> 되고, 성능 때문에 껐던 거라면 그 측정값이 재작성의 근거가 된다.

**결과** 죽은 코드가 남아 읽는 사람을 혼란시킨다. 되살리든 지우든 결론을 내야 한다.

### D-005 — 패킷 큐에 유저 인덱스만 저장
| | |
|---|---|
| 상태 | 확정 |
| 날짜 | (초기) |
| 근거출처 | 코드추정 |

**맥락** I/O 스레드 → 로직 스레드로 패킷을 넘겨야 한다.

**결정** `mInComingPacketUserIndex`에는 `UINT32` 하나만 들어간다.
실제 바이트는 각 `User`의 `PacketBuffer`에 쌓인다. 로직 스레드는 인덱스를 꺼내
해당 유저의 버퍼가 빌 때까지 반복해서 읽는다.

**버린 대안** 큐에 패킷 데이터 자체를 넣기. 큐 원소가 커지고 복사가 늘지만
소유권이 명확해진다.

**결과 / 대가** 이 결정 때문에 `PacketBuffer`가 **두 스레드에 공유된다**.
WorkerThread가 쓰고 ProcessThread가 읽는데 동기화가 없다 (→ R-016).
큐 원소를 작게 만든 대가로 훨씬 미묘한 동시성 문제를 얻었다.
R-016을 고칠 때 이 결정 자체를 재검토할 가치가 있다.

### D-006 — 직렬화 없이 구조체 직접 캐스팅
| | |
|---|---|
| 상태 | 확정 |
| 날짜 | (초기) |
| 근거출처 | 코드추정 |

**맥락** 서버와 클라이언트가 모두 C++이고 모두 x86-64 Windows다.

**결정** `#pragma pack(1)` 고정 크기 구조체를 그대로 `reinterpret_cast`한다.
엔디언 변환도, 가변 길이 필드도 없다.

**버린 대안** Protobuf / FlatBuffers / 수동 직렬화.
스키마 진화와 크로스플랫폼을 얻지만, 지금 필요 없는 능력이고
의존성과 빌드 복잡도가 붙는다. **단일 플랫폼 + 양쪽 다 내가 개발이라는
조건에서 이건 옳은 선택이다.**

**결과 / 대가**
- 신뢰 경계에서 크기 검증이 **필수**가 되는데 빠져 있다 (→ R-005).
  직렬화 라이브러리를 안 쓴 대가는 검증을 직접 하는 것이고, 그걸 안 하면
  선택이 잘못된 게 아니라 미완성인 것이다.
- 구조체 크기를 `static_assert`로 못 박아야 한다 (→ R-012).
- 프로토콜 버전 협상이 없어 클라/서버 버전이 어긋나면 조용히 깨진다 (→ limits.md).

### D-008 — Redis/DB 연동 보류
| | |
|---|---|
| 상태 | 잠정 |
| 날짜 | (미상) |
| 근거출처 | 코드추정 |

**결정** `CorePch.h`의 hiredis include와 `PacketManager::ProcessLoginDBResult`가

### D-009 — 검토는 LLM, 개발은 사람
| | |
|---|---|
| 상태 | 확정 |
| 날짜 | 2026-08-20 |
| 근거출처 | 사람 |

**맥락** 개인 포트폴리오 프로젝트. 평가받는 대상은 코드만이 아니라
**엔지니어링 판단력**이다.

**결정** 사람이 설계·구현하고 LLM은 검토·피드백만 한다.
주고받은 것은 전부 기록한다.

**버린 대안** LLM에게 구현을 맡기고 사람이 리뷰. 속도는 빠르지만
포트폴리오로서의 가치가 사라지고, 무엇보다 사람이 코드를 소유하지 못하게 된다.

**따라오는 규칙** LLM 지적이 100% 채택되는 로그는 **실패한 로그**다.
반려는 결함이 아니라 판단의 증거이므로 반드시 남긴다.

**강제 수단 (2026-08-23 추가)** 이 결정은 대화 중 합의로만 두면 새 세션이나
다른 도구에서 무시된다. 도구별 자동 로드 파일 세 곳에 규칙을 배치했다.

| 파일 | 읽는 도구 | 역할 |
|---|---|---|
| `AGENTS.md` | Codex, Cursor, Amp, Windsurf, Jules 등 | **정본** — 전체 규칙 |
| `CLAUDE.md` | Claude Code | 절대 규칙 + AGENTS.md 포인터 |
| `.github/copilot-instructions.md` | GitHub Copilot | 절대 규칙 + 포인터 |

절대 규칙(코드 수정 금지)만 세 파일에 중복해서 적었다. 나머지는 `AGENTS.md`에만
있다 — 중복은 드리프트를 낳으므로, 절대 누락되면 안 되는 것 하나만 복제한다.

**경계** 금지는 소스 코드에만 적용된다. `docs/**`와 `*.md`는 LLM이 관리한다.
단 사람이 채우기로 한 칸(검토 로그의 **결정**/**결과**, 이 문서의 **버린 대안**)은
LLM이 추측으로 채우지 않는다. 채우는 순간 기록이 증거가 아니라 창작이 된다.

## 반려 기록

LLM의 지적이나 제안 중 검토 후 **채택하지 않기로 한 것**들.
지우지 않는다. 같은 제안이 다시 올라오면 여기를 가리킨다.

```markdown
### X-000 — 반려한 제안 한 줄
| | |
|---|---|
| 원 항목 | R-0XX / (즉석 제안) |
| 날짜 | YYYY-MM-DD |
| 재검토 | 조건 또는 시점, 없으면 "없음" |

**제안 내용** LLM이 뭐라고 했는가.
**반려 사유** 왜 안 하기로 했는가. ← 이 칸이 이 문서의 존재 이유
```

*(아직 없음. 첫 반려가 나오면 여기에 X-001로 기록.)*

      룸 액터 전환의 필요성을 좌우한다)
